# 组件接口兼容与装配连接方案

## 背景与目标

组件平台需要在两个不同场景中判断接口是否可以配合：

- **槽位替换**：候选零部件的接口能否替换组件中定义的基准接口。
- **装配连接**：两个已选接口能否建立指定的 Mate 关系。

两种场景应使用相同的接口契约和配合族规则，但需要分别验证替换语义、Mate 约束及实际装配结果。接口兼容仅表示声明条件允许尝试配合，不代表几何已经正确拼合或无干涉。

目标是消除当前可绕过兼容规则的连接路径；用明确、可扩展的接口配合契约代替字段猜测；统一前端候选筛选、后端写入校验和发布验证的判定语义；为历史接口数据提供可解释的迁移状态。

## 当前实现与问题

- `PartInterface.type` 表示几何载体 `plane`、`axis` 或 `point`；`interfaceType` 表示定位、连接、支撑等语义类别；`locatingType` 表示面接触、同轴、销孔等定位方式。这些概念目前没有形成明确的配合规则。
- 前端 `src/domain/interfaceCompatibility.ts` 要求 `type` 完全相同。它从 `connectionGender` 或旧 tags 推导公母；同一明确公母会拒绝，未知/中性会放行。尺寸统一换算为毫米，双方都缺尺寸也放行；只要一侧未声明尺寸就拒绝。两端都声明连接方式时只按小写文本相等判断。`interfaceType`、`locatingType`、空间方向、坐标系和参数解析后的尺寸均不参与判定。
- `InterfacesStage` 用该函数筛选槽位占用接口，`componentReducer` 和后端 `components/service.py` 在写入槽位时再次检查，`validateComponent` 也检查最终槽位数据。这条路径比普通 Mate 完整，但未知数据被当作兼容，且尺寸与类别规则不足以证明可替换。
- 普通 Mate 的 UI 通过 `connectFirstInterfaces()` 直接选择两个成员的第一个接口。前端 reducer、后端 `mate.add` 和最终 Mate 验证只检查引用存在、成员不同、连接记录不重复及偏置为有限数，没有执行接口兼容检查。
- 前端与 Python 后端分别实现了尺寸、公母、连接方式匹配逻辑。后端当前只在槽位校验中使用兼容逻辑，普通 Mate 没有服务端兼容闸门。
- `AssemblyStage` 明确说明装配求解尚未接入；现有 Mate 只记录声明，不会改变成员位姿，也不能验证接触、同轴误差或实体干涉。

因此现有“兼容”是宽松的元数据筛选，不是 CAD 配合证明；尤其槽位双方缺尺寸、或一端公母/连接方式未知时可能被列为可选，普通 Mate 则能完全绕过筛选。

## 核心决策

### 1. 分离几何、功能、配合族与紧固方式

保留 `type` 作为几何实体类别；保留 `interfaceType` 作为工程用途；保留 `locatingType` 作为定位特征描述。新增版本化的 `mating` 契约，专门说明可与何种接口配合。不要从显示名称或自由标签推断可互换性。

建议的新接口数据形状如下，最终字段需与零部件平台发布包共同定版：

```json
{
  "interfaceContractVersion": 1,
  "mating": {
    "family": "pin-hole",
    "role": "pin",
    "standardId": null,
    "connectionMethod": "sliding-fit",
    "dimensions": {
      "diameter": { "nominal": 10, "lowerTolerance": -0.02, "upperTolerance": 0, "unit": "mm" }
    },
    "frame": {
      "origin": [0, 0, 0],
      "axis": [0, 0, 1],
      "normal": null,
      "coordinateSystem": "part"
    },
    "allowedRelations": ["同轴", "插入"]
  }
}
```

字段含义：

- `family` 是配合规则注册表中的稳定 ID，例如 `plane-contact`、`coaxial-fit`、`pin-hole`、`bolt-pattern`、`rail-slot`。`custom` 需带命名空间和显式适配器版本，未识别 family 不得默认为通用兼容。
- `role` 是该 family 定义的互补角色，例如 pin/hole；不能把公/母当作适用于所有工程连接的通用规则。
- `standardId` 标记螺纹、型材系统、孔系等标准化系列。只有同一标准或规则明确声明兼容的标准才能通过。
- 尺寸使用带上下偏差的名义值，单位必填。参数驱动尺寸可携带受控表达式或解析值；判定必须使用当前参数值及其有效范围。
- `frame` 在零件坐标系内描述配合原点和轴/法向，用于后续姿态约束求解。方向向量应归一化并经过 schema 校验。
- `allowedRelations` 限定该接口支持的 Mate 约束。字段缺失不代表允许任意关系。
- `connectionMethod` 表示真实连接/装配机制，与几何配合族分开。例如接触面可以在几何上相容，但若要求螺栓固定仍需校验孔系和紧固件条件。

既有顶层 `interfaceSize` 可作为迁移期间的数据来源，但新契约发布时不得让含义不明的旧字段继续充当已验证的公差配合。

### 2. 兼容性采用三态与结构化原因

统一函数返回结构化结果，不使用单一布尔值表达所有情况：

```ts
type CompatibilityStatus = "compatible" | "incompatible" | "needs_review";
type CompatibilityAssessment = {
  status: CompatibilityStatus;
  ruleVersion: string;
  checks: Array<{ code: string; status: "pass" | "fail" | "unknown"; message: string }>;
};
```

- **compatible**：双方契约完整，适配器已知，所有必需的类型、尺寸、角色、标准和配合条件通过。
- **incompatible**：存在明确冲突，例如不兼容 family、角色相同但必须互补、尺寸间隙超限、标准不匹配或指定 Mate 不被接口支持。
- **needs_review**：没有发现明确冲突，但关键数据缺失、旧数据无法可靠映射、参数范围跨越兼容边界，或没有对应的配合适配器。

规则不得把未知值当通配符。`needs_review` 不可进入默认可选候选，也不可被最终验证标为通过。可以提供“接受并记录工程例外”的显式操作，但必须填写理由、操作者和规则版本；结果继续标记为 `acceptedWithWarning`，不得改写为 compatible。存在硬冲突时不能用普通确认覆盖，应补全接口契约或实现受控的自定义适配器。

机器可读原因码至少包括 `MISSING_CONTRACT`、`UNKNOWN_FAMILY`、`ROLE_CONFLICT`、`GEOMETRY_KIND_UNSUPPORTED`、`DIMENSION_OUT_OF_TOLERANCE`、`STANDARD_MISMATCH`、`RELATION_NOT_ALLOWED`、`FRAME_INVALID`、`PARAMETER_RANGE_UNRESOLVED`、`SAME_MEMBER`、`ENDPOINT_ALREADY_CONSUMED` 和 `RULE_VERSION_UNSUPPORTED`。界面显示中文说明，API、日志和测试使用稳定原因码。

### 3. 配合族适配器负责专业规则

兼容性引擎只负责规范化、调用适配器、汇总检查项和生成状态。具体物理规则由可版本化的 family adapter 实现。首批建议：

| 配合族 | 必需条件 | 主要几何检查 |
| --- | --- | --- |
| `plane-contact` | 两端声明接触面；支持贴合 Mate | 法向夹角、面间距、有效接触区域重叠及允许偏置 |
| `coaxial-fit` | 两端声明轴线；标准/配合范围明确 | 轴线夹角、径向偏移、直径配合及可允许轴向自由度 |
| `pin-hole` | 角色分别为 pin/hole；两端尺寸已解析 | 最小/最大间隙与公差叠加，轴线误差及插入方向 |
| `bolt-pattern` | 孔数、孔径、孔距/坐标、基准方向完整 | 孔阵列一一映射、位置误差、孔径/紧固件间隙及方向 |
| `rail-slot` | 轨道与槽角色互补；截面或受控 profile ID 明确 | 截面尺寸、间隙、方向、防脱特征及行程范围 |

适配器对需要在局部坐标系中允许旋转、翻转或孔位排列对称的情况，必须明确枚举等价变换，不能通过把尺寸排序后相等来代替几何对应。任何由 `interfaceType`/`locatingType` 产生的语义只能提供候选适配器线索；最终规则必须由契约中的 family 明确确认。

尺寸比较基于区间公差，不用 `max(toleranceA, toleranceB)` 对所有维度统一放宽。以轴孔配合为例，计算孔内径区间与销外径区间的最小/最大间隙，再与该 family / fit class 的许可范围比较。参数化尺寸在当前参数值下检查一次，并在产品要求需要保证全参数域可装配时对参数上下界及关键临界值做范围验证。

### 4. 候选匹配与装配求解分层

第一级是**声明兼容**：只检查契约、尺寸、角色、标准和允许关系，生成可选候选及原因。第二级是**几何求解**：为双方求解刚体变换，使约束关系成立，并检查自由度、冗余约束与约束冲突。第三级是**实体验证**：按需求检查碰撞、穿透、接触面积和装配间隙。

第一阶段实现完成后，产品用语只能表述为“接口声明兼容/可尝试连接”。装配求解和实体验证接入后才可分别报告“约束已求解”和“几何检查通过”。不能把第一阶段的 pass 显示成已成功拼接。

## 写入与验证流程

### 普通 Mate

1. 用户先选定成员和接口 A，再从候选列表选接口 B。候选按接口配合族、允许关系、几何类型和结构化 assessment 过滤；列表展示未通过/待确认原因。
2. 用户选择 Mate relation 与 offset。UI 在提交前检查 `allowedRelations`，但 UI 检查不是安全边界。
3. 前端 reducer、后端草稿服务和最终 `validateComponent` 均对两个指定端点重新调用同语义的兼容判定。服务端拒绝 `incompatible` 与未确认的 `needs_review`，校验成员归属、端点占用策略、Mate 重复与偏置范围。
4. 若允许接受 `needs_review` 例外，提交独立的例外操作或显式 assessment 字段，要求理由；服务端校验并保存审计信息。例外不能隐藏在一个布尔 override 中。
5. 连接展示两端成员和接口名称、配合族、状态、未决项和 relation；移除/改动接口参数后重新评估连接状态。

移除“连接前两个接口”快捷路径，或将其改造成可审阅的候选选择器；不得自动取 `interfaces[0]` 建立 Mate。

### 可替换槽位

基准接口与占用接口使用相同 adapter。只有 assessment 为 `compatible` 的接口进入默认选择列表。`needs_review` 与 `incompatible` 分区显示原因，但不可被普通选择器提交。服务端 `slot.patch`、最终验证和发布预检重新判定；槽位基准或占用接口参数变更后将原分配标为待复核。

槽位表达“替换边界的契约相容”，Mate 表达“两个具体实例之间的约束”。不得因为槽位候选兼容就自动建立 Mate，也不得用 Mate 的几何成功反推两个产品版本可任意替换。

### 端点使用策略

接口契约声明 `capacity` 或 `reusePolicy`：默认一个刚性连接端点只参与一个独立 Mate；平面基准、阵列接口等允许多个约束的情形由 adapter 明确允许并避免过约束。槽位占用沿用当前“一接口只能占一个槽位”规则。validation 必须结合 family 检查占用，而不是只依赖 UI 过滤。

## 前后端边界与数据迁移

- Python 服务端是草稿写入与发布校验的权威边界；TypeScript 前端保留同步本地算法以即时筛选。两端实现同一 `ruleVersion` 语义，使用共享 JSON 契约测试向量和稳定原因码逐条校验。规则目录中的 family ID、允许角色/关系和版本需可追踪；任何一端不支持文档声明的规则版本时返回 `needs_review`/拒绝写入，不能降级放行。
- 将重复的前端槽位算法和后端 `interfaces_compatible()` 收敛到新 `assessInterfaceCompatibility()` 语义。Python 的 `mate.add`、TypeScript 的 `mate.add`、槽位分配、最终 validation、MCP action 与发布前检验均调用相应实现；共享测试向量防止不同步。
- 组件文档与发布包采用向后兼容的可选 `interfaceContractVersion`/`mating` 字段，完成全链路保存、加载、成员预览、接口继承、JSON 导出和 API 模型透传后，再将新组件契约版本升级。组件对外 port 必须继承完整契约快照，且继续校验快照与来源一致。
- 历史发布包和草稿不得被静默改写。已知旧字段可提供迁移建议，但 tags、名称和同类型尺寸只能生成未确认草稿，不能自动生成通过状态。没有新契约的历史接口评为 `needs_review`；既有已发布版本仍可读取和预览。
- 历史 Mate 在读取时标记 `legacy-unassessed`，不伪造已通过的 compatibility assessment。新的 Mate 写入受新规则约束。新版本发布时，是否允许保留未评估的旧 Mate，应由发布策略明确：默认阻止新发布并逐项复核；只查看历史版本不触发数据迁移。
- 保存 Mate 的 assessment `ruleVersion` 和通过的关键检查摘要，或在加载时重算并记录所用版本。最终发布必须可追溯所用契约与规则版本。

## 用户界面

- 接口清单把几何载体、用途、配合族、角色、标准、尺寸/公差、坐标基准、允许 Mate 和元数据完整度分开展示。
- Mate 编辑器提供“选择接口 A / 选择接口 B / 配合关系”步骤；选择 A 后只突出兼容候选，并可切换查看待确认和不兼容项及原因。兼容候选按接口呈现，不只高亮整个成员。
- 槽位选择器展示兼容状态、family 和关键尺寸匹配信息。未知字段标“待确认”，不可显示为绿色兼容。
- 验证面板按 Mate、槽位列出机器原因码对应的中文诊断与修正建议。示例：“孔径范围 9.98–10.00 mm 与销径范围 10.00–10.02 mm 重叠，最小间隙 -0.04 mm；需调整公差或选择其他接口。”
- 未接入求解器前，对已保存 Mate 显示“声明兼容，未求解”；界面继续明确位置不会自动改变。

## 分阶段实施

### 阶段 A：关闭当前绕过路径

- 将 `connectFirstInterfaces()` 替换为显式接口对选择，不再选择数组首项。
- 对现有规则先做最小收紧：新 Mate 必须通过现有兼容判断；普通 Mate 写入、槽位写入和最终验证均执行；尺寸双方未声明或关键字段未知时返回待确认，不能自动作为通过候选。
- 后端服务拒绝不兼容 Mate；前端 reducer 与 UI 同步防护。针对历史 Mate 使用 legacy 状态，不影响读取。
- 确保错误通过共享草稿同步/MCP 路径时能返回明确状态，而不是静默忽略或覆盖用户编辑。

### 阶段 B：接口契约与基础适配器

- 在前后端 schema 和发布包中透传版本化 `mating` 契约，补齐兼容/迁移状态。
- 实现 `plane-contact`、`coaxial-fit` 和 `pin-hole` 的明确角色、尺寸、公差和 relation 检查；未支持 family 保持待确认。
- 增加服务端权威检查、规则版本和结构化诊断；发布预检报告所有待确认 Mate/槽位。

### 阶段 C：复杂接口与几何求解

- 实现 `bolt-pattern`、`rail-slot` 等有具体业务数据支撑的 adapter，不为未验证的 family 提供通用放行规则。
- 引入接口参考帧求解、约束冲突/自由度诊断，再按需增加实体碰撞与装配间隙验证。
- 按 family 的实际需求配置多 Mate 使用能力、对称变换和参数范围证明。

各阶段独立发布；阶段 A 必须先于任何把当前 Mate 显示为兼容或拼接成功的产品改动。

## 测试与验收

### 共享契约向量

为每种 adapter 提供 JSON 输入、预期状态、原因码和规则版本。前端与后端在同一组向量上运行。必须覆盖：

- 明确兼容与明确冲突；同角色/异角色、未知角色、未知 family 和不支持 ruleVersion。
- 单位转换、非标准单位拒绝、上下公差与最小/最大间隙、容差边界、矩形旋转/对称、参数边界和未解析表达式。
- 平面法向相反/相同、轴线同向/反向、角度误差和偏移、插入方向、bolt pattern 缺孔/孔距不匹配。
- `interfaceType`/`locatingType` 相同但 mating family 冲突的情况，证明语义标签不会单独放行。
- tags 中有 `male`/`female` 或“公/母”但缺少新契约时仍为 `needs_review`。

### 集成测试

- reducer 和服务端均拒绝不兼容 Mate、待确认 Mate、同成员连接、不允许的 relation、重复/超容量端点；有效连接可以保存并被最终 validation 接受。
- 直接调用服务端/API/MCP 不能绕过客户端规则。
- `mate.add` 更新时验证的确切两个接口必须与请求一致；不能错误复用成员级“存在任一兼容接口”结果。
- 槽位候选列表、槽位写入、发布验证使用相同 assessment；修改基准或参数后旧分配不能继续无提示显示通过。
- 历史组件/发布包可读取、预览和导出；历史 Mate 显示 legacy 未评估，不会被转换为新规则通过。
- UI 状态清楚区分兼容、待确认、不兼容、声明兼容但未求解、求解通过和实体检查通过。

### 完成标准

- 新建 Mate 没有通过明确选择的两个接口和服务端规则校验不能保存。
- 尺寸、公差、配合族或允许关系缺失时不自动判兼容。
- 前端候选、后端写入、最终组件验证和发布预检对同一输入给出相同规则版本和状态。
- 现有发布版本字节与历史草稿保持不变；任何迁移建议都可审阅、可取消。
- 未实现几何求解时，系统不会宣称接口已实际拼合或工程检查已通过。

## 非目标

- 本方案不要求所有接口都必须用公母属性；角色由具体配合族定义。
- 本方案不把接口元数据兼容等同于整体结构强度、制造可行性或法规符合性验证。
- 本方案不自动修改历史发布包、组件固定引用、成员位姿或用户创建的连接关系。
- 在几何求解器与实体模型校验实现之前，不承诺自动把两个零件移动到正确的装配位置。
